5. 关键流程

daemon 启动

  1. 验证 profile，取得排他生命周期租约；vault 文件锁等待最多 30 秒。
  2. 读取当前 protocol-v5 hashed 运行锁；只有在排他租约下安全删除畸形的当前 v5 候选并重读后得到 Removed/Absent，才可继续。Changed/Contended、Unix raw legacy、旧 v4/v3 和其他旧/未知协议都 fail closed。
  3. 目标 profile 的 Argon2id KEK 解包 {DEK, AuthSeed, profile_id, generation}；DEK 解密 SSH 凭据，AuthSeed 按 name + profile_id + generation 派生 scoped call key。首次连接先 KEX/观测 host key，在排他租约下原子写 pin，只有写入成功后才发 SSH 密码。TOFU 只以 fresh nonce 重封同一 identity/package，不推进 generation，避免使刚建立的 daemon 立即失效。SSH 建立后清除 profile 口令与 key package，只保留 SSH session/password snapshot 与 call key。
  4. UI 从最初 status probe 起使用单一 30 秒 absolute deadline。listener bind 与 lock publication 在 owned blocking worker 内完成；原子写锁前就 arm token-CAS cleanup guard，并持有排他租约。
  5. readiness 通过 oneshot 交接所有权；receiver 消失会 invalidate SSH 并清理已发布 runtime。ready 与 daemon ended 同时发生时偏向先发 Started。成功后进入 64 连接/8 重结果槽 accept loop。

IPC v5 互认证与精确调用授权

  1. 客户端从受保护锁读取 PID、endpoint 和随机 token，验证 endpoint 派生值。对敏感根操作，它在 connect 前用本次目标 profile 口令认证 key package 并从 AuthSeed 派生 call key；错误口令因而产生零 IPC 字节和零 SSH 副作用。
  2. 连接后、发送认证帧前核对 OS 对端 PID/UID；交换 AuthHello、AuthChallenge、AuthResponse、AuthAccepted。
  3. token proof 绑定 generation/endpoint/profile/version/双方 nonce；call proof 使用按 (name, profile_id, generation) 域分离的 key，并绑定由规范根请求每个字段生成的 HMAC intent commitment。client 在验证 server call proof 和 Accepted 前不发送业务帧。
  4. daemon 读取真正根帧后重新核对精确 intent，且每个连接只消费一个根请求；替换、重放、token-only 敏感调用均在 SSH/listener 副作用前静默关闭，不提供结构化授权 oracle。

exec

  1. 校验命令不含 NUL 且不超过 64 KiB，建立 absolute deadline并只路由一次。
  2. deadline 覆盖 IPC、重结果槽等待、单飞重连、DNS/TCP/KEX/auth、channel open、exec request、输出与退出状态。
  3. IPC writer 在每次 poll_write 与 poll_flush 前都检查同一 absolute deadline，避免外层 timeout 对 ready inner Future 的最后一次 poll 越过预算。只有 4 字节长度头和完整序列化 payload 都被 AsyncWrite 成功接收后、flush 前才跨过提交边界。序列化失败、零字节/部分帧写失败和完整帧前 deadline 都是确定的 pre-submit；完整帧后的 flush/响应失败、deadline 或断开属于 typed ExecOutcomeUnknown。
  4. v5 daemon 的普通 Error 只表示已确认尚未把请求交给 russh，post-submit 错误必须编码为 typed unknown；v5 client 拒绝 v4 及更早锁/挑战，避免旧版本语义混跑。
  5. 直连 russh 的 bounded exec-send 在每一次 poll 前检查 absolute deadline，只有内部请求成功入队才跨提交边界；Pending 不能越过预算后再触发远端执行。只接受明确且唯一的 ExitStatus，无退出码、重复退出码和输出超 8 MiB均失败且在已提交后属于结果未知。
  6. 异常退出依次有界尝试 TERM、短宽限、KILL、EOF、Close 和关闭确认；不能确认时使 transport 失效。

创建目录

  1. IPC 请求沿用完整 frame 提交边界；direct SFTP MKDIR 从第一次实际 poll 起记录 request may have reached remote。两条路径都在每次 mutation poll 前检查 absolute deadline。
  2. 显式且请求 ID 匹配的 SFTP STATUS 拒绝，以及 daemon 在 validation/session setup 或该显式 STATUS 后返回的普通 Error，是明确未创建的 plain rejection。
  3. 请求可能已到达后若 deadline、EOF、unexpected response 或 transport/protocol 错误阻止确认，则返回 typed CreateDirOutcomeUnknown，使旧 transport 失效，并要求检查远端路径后再重试。

上传

  1. 在任何路由/SSH 之前只打开一次本地普通文件，保留稳定 handle 与 size。
  2. 远端同目录以 CREATE | EXCLUDE 和 0600 创建随机 partial；CREATE 首次被 poll 后即保守记录 partial 可能存在，只有显式且匹配请求的 SFTP STATUS 拒绝能证明未创建。其他 deadline/断开/协议错误继续进入清理。
  3. partial CREATE、逐块 WRITE、flush、shutdown、hardlink commit 与 unlink cleanup 的 Future 均在每次 poll 前检查对应 absolute deadline，防止 Pending 在预算之后才产生副作用。
  4. commit 强制使用 hardlink@openssh.com 的 no-replace 语义；扩展缺失或返回错误时失败关闭，绝不回退到无法证明 no-overwrite 的 SFTP v3 RENAME。
  5. commit 确认后即使临时名删除被打断也报告已提交；UploadEnd 周围的响应丢失有 2.25 秒对账，否则返回 typed UploadCommitOutcomeUnknown。
  6. 直连上传的 owned worker 在外层 Future timeout/drop 后继续拥有 fresh-channel 清理；commit 已开始后的 Finished(Err) 也是 outcome unknown，不是确定未提交。

下载

  1. 受保护 CREATE_NEW 一成功就立即 arm CreatedFileRollback，再验证 owner/type/ACL；错误或 panic 只删除稳定身份确认的新对象。
  2. 读取远端内容、核对字节数、flush、sync_all。
  3. 同目录 hard link 原子安装最终名；已存在时不覆盖，并以稳定 handle 对账最终对象身份。
  4. 本地 partial create 在 owned blocking worker 内返回 UnclaimedLocalPartial；未 claim 结果在 cancel/timeout/drop/unwind 下仍由 Drop 调度清理，claim 交接中间无 await。

交互 shell

PTY 列数和行数由 direct、IPC client 与 daemon 统一限制为 1..=10000，非法尺寸在 I/O 前拒绝。打开 shell 的精确根请求需要目标 profile 口令/call-key 授权一次；建立后按键与输入帧继承该会话授权，不重复 KDF。直连 SSH+PTY setup 共用 30 秒 deadline；IPC client 的 Shell/Ack 上限为 32 秒，daemon 内部仍为 30 秒。client/daemon 在整个 IPC shell 中各自保留一个 pinned frame decoder，避免 cancel/drop 卡在 header/body 中间时丢失 framing；等待满队列和已入队的 channel element 都有 RAII zeroize envelope。CLI stdin 以 100 ms crossterm::poll 响应取消，忽略 key release，接受 press/repeat；raw mode 由 RAII guard 持有，正常返回、错误、任务 abort 或 unwind 都会尝试恢复终端。setup 成功后的会话没有整体 deadline。

SSH tunnel

  1. 启动根请求只绑定模式、监听端口、L/R 目标端口和每 tunnel 连接上限；地址字段已从 TunnelSpec 删除，listener 与 L/R target 由两端固定为 127.0.0.1。CLI 每次 tunnel 调用验证目标 profile 口令；UI 必须持有该 profile 当前 generation 的有效五分钟授权。
  2. -L：本机 127.0.0.1 listener → SSH direct-tcpip → 已连接 SSH 主机的 127.0.0.1:目标端口；-D：本机回环 SOCKS5 NO AUTH/CONNECT（IPv4/IPv6/受限 ASCII 域名）→ direct-tcpip，可访问该 SSH 主机能够到达的任意远端目标；-R：SSH 主机 127.0.0.1 listener → registered forwarded-tcpip → 本机 127.0.0.1:目标端口。
  3. payload 在 socket 与 russh channel 间直接双向 copy，不穿过 IPC。daemon IPC 只保留授权/lifetime control；EOF、TunnelStop、daemon shutdown 或 UI/CLI cancel 触发回收。
  4. 所有 listener 强制 loopback，port 0 可由系统分配；没有 bind/expose 输入或外部监听路径。每 tunnel 默认 32、硬上限 128；每 SSH session 合计 256 live flow；-R pending queue 32；daemon tunnel control 8。
  5. 所有 channel open/forward/cancel/listener bind/remote target accept 均使用 per-poll hard deadline。停止先 drain 2 秒，再给 forward cancel/task 4 秒；client 清理 7 秒，UI exit 8 秒。Drop 路径只做非阻塞 cancel；cancel 结果不确定、unknown/orphan server-opened channel 会 invalidate transport。

Tunnel 公共选项只有 --port 0 与 --max-connections 32；连接上限硬限制为 128。--bind、--expose、--target-host 均不存在。所有 listener 与 L/R target 固定为 127.0.0.1；port 0 的最终地址/端口在 ready 后打印。

普通 profile 操作在每次 CLI 进程调用中重新验证目标独立口令，不跨调用缓存；list 与 admin status 是 catalog/policy metadata-only。status/down 在 IPC connect 前按目标 (name, profile_id, generation) 派生 call key，再执行精确 intent 授权。shell/tunnel 建立后，按键和后续 TCP 流不会重复询问。v4 没有共享 change-master/rekey。

CLI 的随机口令采用“先交付、后提交”：rotate-random 及带 --random 的 admin reset 必须提供 --random-output。输出必须是 vault 目录外、不得预先存在的绝对路径；程序以受保护 create-new 文件严格写入 UTF-8 passphrase + newline，同句柄同步/回读成功后才修改 vault。输出失败时旧口令和 generation 不变；若之后 vault commit 失败，文件保留但该口令尚未生效，操作者必须以命令成功状态为准后再导入密码管理器/销毁过渡文件。非 Windows 的 v2 migration 与 admin-reset --media 在捕获命令秘密前即拒绝。

SERCTL_SSH_PASS、SERCTL_PROFILE_PASS、SERCTL_ADMIN_PASS、SERCTL_LEGACY_MASTER 与兼容变量 SERCTL_MASTER 在任何可失败 Unicode 解码和异步 runtime 前先快照，再从本进程环境一并删除；任一值无效也不会留下其他值。SERCTL_MASTER 仅按命令路由为普通 profile 口令或 v2 旧 master。环境继承本身不是秘密通道。Clap 的动态错误、anyhow 链、日志和程序生成字段会转义控制字符。

终端信任边界：exec stdout/stderr 与 PTY 输出来自远端，被设计为原样交互数据，可能包含 ANSI/OSC。对不可信服务器应重定向到文件、使用 download 或先做独立转义，不要直接显示到高权限终端。

  • CLI 随机口令不是“先改 vault、再打印结果”：受保护的 create-new 输出完成 sync_all、常量时间同句柄回读（Unix 再同步父目录）后，闭包才执行 profile mutation。交付阶段失败时 vault 保持原口令；mutation 失败时输出文件保留为尚未生效的孤立 receipt，避免把 profile 锁在调用者从未取得的随机值后。该顺序只保证非对抗 I/O：同 UID 对手仍可在回读后删除/换名文件，或替换其可写父目录，不能把“路径仍由调用者持有”视为密码学保证。
  • Linux 跨用户管理只开放 CLI 破坏性 reset。进程仍为 euid 0 时按传入账号名通过 NSS 解析 UID/GID/home，拒绝 root、任意 UID/HOME/SUDO_USER/路径输入，使用 O_NOFOLLOW 句柄验证 home 非宽松可写且现有 .serctl 由目标账号独占；随后清空 supplementary groups，并把 real/effective/saved GID/UID 全部不可逆降为该账号，在创建 Tokio worker 和打开 vault 字节前核对降权结果。进程内委托标志只允许丢弃并替换旧秘密，不赋予保留式恢复能力。
  • 密码校验、profile 加解密、vault 更新和运行锁写入的敏感 JSON使用两遍序列化：第一遍仅计数，第二遍写入精确预分配的 Zeroizing<Vec<u8>>。IPC frame 同样不先生成普通敏感 Vec。
  • 可控明文、命令、帧、输出和缓冲在 Drop/错误路径清零；这不能清除 allocator、OS cache、第三方库、swap 或 crash dump 中的副本。
  • vault 更新和运行锁发布共用同目录受保护原子替换；vault 文件锁采用 try_lock 轮询且最多等待 30 秒。Unix 同步临时文件后原子 rename，再 fsync 父目录；Windows 从临时文件创建时即施加 protected DACL，sync_all 后持有稳定、已验证的受保护父目录句柄，并调用 Microsoft MoveFileExW（MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH）。
  • 注入提交失败会保留旧目标并清理临时文件；Windows 本机测试还核对成功内容与 DACL。该证据验证 API 的写穿/同步路径和故障保持性，不是实际断电模拟，也不把 OS、文件系统或硬件之外的持久性当作已证明。

Windows 2-of-2 恢复、v2 迁移与回滚边界

  • 初始化产生一个规范 X25519 私有输入并拆成两个非零 XOR share：本地 share 只以超管密码 KEK 加密后进入 vault，另一 share 以 canonical JSON 写入新 U 盘文件。组合两份 share 后只用于 X25519 + HKDF 派生 recovery-envelope AEAD key；不会还原或显示旧 profile 口令。
  • 公开 recovery configuration 本身不保密，但必须防替换。AdminSecret 在超管密文中保存完整 canonical configuration 的 SHA-256 digest；每个 profile 同时保存以其 AuthSeed 对完整 configuration 计算的 HMAC-SHA256 tag。超管验证、profile 口令验证、call-key 派生、编辑/轮转/TOFU 和 recovery rotation 均先核对相应绑定，避免管理员只换 public key 后诱使后续正常更新把新 package 密封到攻击者密钥。
  • 保留式恢复要求超管密码、匹配介质和新 profile 口令三者齐全；serctl 打开旧 package/凭据后保留 profile ID，立即生成 fresh package/递增 generation 并重新封装。单独超管密码只能验证管理权或执行明确的破坏性替换，单独介质也不能打开 envelope。
  • 恢复轮转先用旧 2-of-2 组合认证每个 profile package/payload，生成全新配置与全部 envelope，create-new 持久化新介质，最后一次原子提交 vault。CLI/UI 都要求绝对路径，在同一稳定普通文件 handle 上同步并常量时间回读核对，拒绝 link/reparse 以及 `.serctl` vault 内部输入/输出，Unix 还同步父目录。失败最多留下孤立新介质；旧介质只在 vault 成功提交后失效。
  • 绝对路径、create-new、文件类型和回读只能证明文件操作约束，不能证明目标卷确是 USB、与主机物理分离、不可复制或使用后已弹出。操作者必须把介质放在与 vault 及其备份分离的可移动存储上，写后核验、弹出并离线保管；UI 的“U 盘”提示不是硬件证明。
  • v2→v4 只支持全量、离线、一次性迁移。Windows 验证旧共享 master，要求 profile 集合与新独立口令集合精确相等，拒绝未认证 format-0 记录，并为每条转换记录生成随机 128 位 ID；UI/CLI 明确报告校验、独占访问、旧库认证、逐 profile KDF、介质持久化和原子提交阶段，介质路径在取走输入秘密及执行 KDF 前预检。全局 runtime barrier/lease、全部认证转换与新介质持久化都成功后才替换 vault。Linux 路径在 root-owned system share store 与明确目标用户边界实现前失败关闭。
  • 开发过程中的中间 vault/record v3 从未发布，且其 AAD/KeyPackage 布局与最终 v4 不同；v4 对 v3 的 load、catalog 与 migration 均失败关闭，不会把 v3 猜作 v2、补默认 ID 或自动迁移。需要该临时数据时只能使用匹配的开发期 binary/备份离线处置。
  • (name, profile_id, generation) 认证绑定当前记录实例并防 UI/IPC 中的陈旧授权、跨 profile 重放、同名删除重建复用和常规并发覆盖；generation 不是 TPM/远端单调计数器。拥有 vault 文件写权限的管理员若恢复整份内部一致的旧 vault.json，当前实现无法检测该完整快照回滚。

稳定句柄与平台权限

  • Unix：安全目录/文件以 O_NOFOLLOW | O_NONBLOCK 打开，在相同 handle 上验证 regular/type、effective UID和 0700/0600。
  • Windows：目录/文件拒绝 reparse，并使用禁止继承的 owner/SYSTEM/Administrators protected DACL；失败关闭。对象 owner 必须匹配当前进程令牌的 TokenUser 或 TokenOwner。后者兼容提升令牌以 BUILTIN\Administrators 作为默认 owner 的正常对象，同时仍拒绝与本令牌无关的 SID，不扩大 protected DACL 已明确包含的管理员边界。
  • 只读运行锁在首次读取前就建立 Zeroizing 缓冲，一次预分配 64 KiB + 1，避免增长/realloc 时释放含 token 前缀的旧 allocation；稳定 handle 上的二次上限读取阻断 metadata 后增长竞态。

租约与畸形锁恢复

daemon 生命周期和 profile 变更使用排他租约；普通直连使用共享租约。profile mutation 只有在排他锁实际返回 contention 时才显示“正在被 direct operation 或 daemon 使用”；打开 lease、owner/ACL 或其他 I/O 失败保留真实错误链，不再被一律误包装为占用。首次 TOFU 时，直连与 daemon 都先 KEX/观测 key，在排他租约下原子只写一次 pin，之后才发送 SSH password。假 server E2E 已验证 pin 写入失败时不会看到 auth request。

当前 protocol-v5 hashed 运行锁若无法解析，清理器必须先取得同一排他生命周期租约，再验证 runtime 目录及文件权限/类型并重读 namespace。对账结果只有 Removed/Absent 允许进入 direct fallback；Changed/Contended 均 fail closed。旧 v4、v3、protocol 0/2 与未知版本锁在连接前拒绝且保留，不按“畸形当前锁”清理；Unix 上被遮蔽的 raw legacy 锁仍会拒绝，Windows 不探测不安全的 raw legacy 名称。

9. IPC v5：统一抽象、双向认证与调用授权

传输与 OS 边界

  • Windows Named Pipe 和 Unix Domain Socket 对上层暴露同一 AsyncRead/AsyncWrite、listener、connect 与长度前缀 JSON frame API，不存在两套业务协议。
  • Windows 每一个 pipe instance（包括 accept 后预建的下一实例）都在创建时传入禁止继承、仅 owner/SYSTEM/Administrators 的 DACL，并拒绝远程客户端。
  • Unix socket 位于 0700 runtime 目录，socket mode 为 0600。
  • 认证前客户端用 GetNamedPipeServerProcessId 核对 server PID；Unix 用 peer credentials 核对当前 euid，且 PID 必须存在并与锁中 PID 匹配；无法提供 PID 的目标失败关闭。

四帧 token + profile call-key HMAC-SHA256

client  → AuthHello(version=5, client_nonce, intent_commitment?)
daemon  → AuthChallenge(version=5, server_nonce, server_proof, server_call_proof?)
client  → AuthResponse(client_proof, client_call_proof?)
daemon  → AuthAccepted

运行锁 token 的 client/server proof 绑定独立 role domain、版本、profile、派生 endpoint id、双方 nonce 和可选 intent commitment，负责证明 daemon instance/endpoint。远程敏感根请求还增加由 profile call key 生成的 server/client call proof；v4 call key 从 KeyPackage 的 AuthSeed 按固定 domain + profile name + 128-bit profile_id + generation 派生，不在 IPC、vault 或运行锁中传输/持久化。所有 32 字节值要求规范 padded Base64，nonce 不得相等，proof/commitment 常量时间比较。

intent commitment 是 call key 对规范根请求摘要的 HMAC，覆盖操作 tag 及每个安全字段：exec command/deadline、PTY size、SFTP path/deadline、upload size，以及 tunnel mode/listener port/L-R target port/max connections。地址不进入 TunnelSpec 或摘要，两端固定使用 127.0.0.1。client 必须先验证 server token proof、server call proof并收到 AuthAccepted，才发送真正根帧；daemon 再根据实际根帧核对 commitment，核对前不会触发参数验证后的 SSH、listener 或远端副作用。上下文消费后不能授权第二个根请求；upload chunk、shell input、tunnel stop 只能继承已经授权的生命周期。

控制请求同样授权：Status/Shutdown 必须携带目标 (name, profile_id, generation) 的 call-key 与精确 intent；token-only 四帧握手不能消费任何业务根帧。UI refresh 可无口令读取明文 catalog，但只为仍持有匹配 grant 的记录派生 call key 并探测 Status；没有有效授权的退出不会绕过协议停止持久 daemon。Status 只返回 profile/host/user/started metadata，不探测 SSH、不使用 retained password、不触发 reconnect。
v5 切换边界：v5 没有 v4 或更早版本的 dual-stack；endpoint/domain 与运行锁 protocol 均已升级。v5 client 看到旧 v4、v3、protocol 0/2 或未知锁时在 connect 前 fail closed、保留证据且不直连 fallback。必须先用与活动旧 daemon 匹配的旧 binary 正常停止，再整体切换 client/daemon。

11. 目录浏览与传输完整性

统一 SFTP frame guard

高层 russh-sftp 和自实现目录 reader 均通过相同 bounded stream。每个 SFTP 长度前缀一到达就先检查 body 不超过 1 MiB；超限时不读取/分配声明 body，立刻标记 transport 失效并触发代理取消。SFTP init 卡住仍由外层 absolute deadline 兜底。

流式目录列表

  • 直接执行 SFTP v3 REALPATH、OPENDIR、重复 READDIR、CLOSE，不调用先聚合任意结果的便捷 API。
  • 协议 packet encoded body 累计最多 8 MiB；canonical path、name 与完整 path 的保留字符串合计最多 2 MiB；entry 最多 10,000。
  • 拒绝空名、绝对名、包含 /、.. escape 或 NUL 的 entry component。
  • 排序一次性缓存小写 key，避免比较器重复分配；最终以真实 DirList JSON 序列化大小验证 16 MiB IPC wire 上限，覆盖控制字符六倍转义最坏情形。
  • daemon 与 direct 使用同一 reader/预算；解析或预算失败会关闭 channel 并使 transport 失效，下一请求通过单飞重连恢复。

远端上传

  • 目标/临时路径长度和 NUL 被统一验证；临时名预留完整 45 字节后缀。
  • partial 使用 SFTP CREATE | EXCLUDE | WRITE，创建属性 0600，因此没有服务器默认常见 0644 的暴露窗口。CREATE 首次被 poll 后就视为可能创建；只有匹配请求的显式 SFTP STATUS 拒绝证明未创建，transport/protocol/deadline 错误必须继续清理。
  • CREATE、逐块 WRITE、flush、shutdown、hardlink 与 remove-file cleanup 都通过 mutation guard，在每一次 poll 前检查所属 absolute deadline；外层 timeout 不会在截止点再 poll 一个刚变 ready 的副作用 Future。
  • 优先 OpenSSH hardlink@openssh.com。扩展被声明却报错时，不尝试 rename，以免“目标存在”被错误降级成覆盖路径。
  • 扩展未声明或返回错误时失败关闭；不再使用无法跨服务端实现证明 no-overwrite 的 SFTP v3 RENAME fallback。
  • hardlink 成功即记录 committed，再尝试 unlink 本方 partial；删除失败不会把已安装目标倒退成失败。直连 worker 在 commit_started 后的 timeout/cancel 或 Finished(Err) 而未确认 committed 时，均返回 typed UploadCommitOutcomeUnknown。

本地上传源

源文件在 daemon/direct 路由和 SSH 认证前只打开一次，后续始终读取同一 handle。Unix 用 O_NONBLOCK 后 fstat 拒绝 FIFO、设备、目录，允许最终指向普通文件的 symlink；Windows 用 OPEN_REPARSE_POINT 并拒绝 reparse/设备/目录。程序不改变用户源文件 ACL。

本地下载

  • partial 以随机同目录名称和 atomic create_new 建立；创建成功一返回就 arm CreatedFileRollback，所以后续验证错误/panic 也会回滚。Unix 用 dev/inode 保留同名替换对象，Windows 用稳定 handle 删除原创建对象；碰撞不会误删。
  • Unix 从创建瞬间即 owner-only 0600，并在 handle 上核对 UID/type/mode。Windows 在 CREATE_NEW 时通过 SECURITY_ATTRIBUTES 应用 protected owner/SYSTEM/Administrators DACL，再验证 owner/DACL/reparse/type。
  • 本地 create 由 owned spawn_blocking 返回 UnclaimedLocalPartial；异步 Future 在 cancel/timeout/drop/unwind 下未 claim 时，Drop 仍会调度清理，claim 交接中间没有 await。blocking pool 饱和会延迟但不放弃清理；无法创建清理线程时可能保留路径。
  • 传输完成后 flush + sync_all，再以 hard link 原子 no-replace 安装最终名称。Windows 在 clone path/spawn 不可逆 hardlink worker 之前先复查 now < deadline，避免 elapsed deadline 下 timeout_at 仍先 poll ready inner；安装后在有界 blocking worker 内对稳定 handle 调用 GetFileInformationByHandle 对账。
  • hard link 不可用时安全失败而不是退化为可覆盖 rename；磁盘耗尽/文件系统故障也会保留明确错误。
内容级边界：当前验证字节数、权限、提交身份和 no-overwrite，不实现远端 fsync 协议或 evidence 内容签名。审计流程仍应独立计算/核对 SHA-256 或数字签名。

12. SSH 算法、隧道、存活与重连

  • 依赖 russh 0.62.5，关闭默认 feature 并只启用 ring 后端；KEX/MAC 沿用 russh 当前安全默认。
  • server host-key 签名仅允许 Ed25519、ECDSA、RSA-SHA2-256 与 RSA-SHA2-512；没有 hash 标识的 ssh-rsa SHA-1 被明确过滤。
  • SSH host key 使用 SHA-256 fingerprint。首次 TOFU 按 KEX/观测 key → 排他租约下原子 pin → 发送 password 的顺序执行；pin 失败时在 auth 前中止 transport。russh password-auth send 的 bounded Future 在每次 poll 前检查 absolute deadline，Pending 不能在预算之后才披露密码。之后所有连接/重连都要求一致。
  • TCP 经双向 copy proxy 交给 russh。deadline 或 cancel 会关闭 proxy 两端并等待退出，解决 russh 在 KEX 前已 spawn session task、丢弃 connect Future 仍可能泄漏的问题。
  • keepalive 每 30 秒发送，连续 3 次无响应后连接失效；SessionManager 通过 Mutex 单飞重连，等待锁、DNS/TCP/KEX/auth 全部消耗调用者剩余 deadline。
  • 在途请求持有旧 Arc<SshSession>；替换不会从请求下方移动对象。不可安全取消的 channel-open/SFTP-init 超时会 invalidate 整个旧 transport。
  • Status 有意只报告 daemon lifetime metadata，不取得 SSH session、不 reconnect。调用本身仍经过 call-key exact-intent 授权，因此 Status 表示“daemon 在运行”，不是 SSH health probe。
  • 本地 L listener、动态 D listener、远程 R listener，以及 L/R 的固定 target 地址全部是 127.0.0.1；地址不由调用者提供。L/D 的每个 flow 通过 direct-tcpip；远程 forward 使用 tcpip-forward/cancel-tcpip-forward 与 generation-aware bounded registry，只接收当前注册 port 的 forwarded-tcpip。其他 server-opened session/X11/agent/streamlocal/unknown channel 均显式拒绝。
  • 每 tunnel 连接 semaphore 与每 SSH session 256-flow aggregate semaphore 都在 accept 后以非等待方式取得，满载时拒绝新 socket/channel，不把 listener loop 堵死。远程 pending channel 为 32；旧 generation removal 不能删除新 route。
  • 每个 flow 的 payload 直接 copy_bidirectional；单 flow 错误通常只结束该 flow。forward/cancel/channel 状态不确定或 orphan/unknown channel 则 invalidate transport，宁可断开共享 SSH 也不遗留未受控的远程 listener/channel。

14. 残余风险与信任边界

R1 · TOFU 首次 MITM

固有

第一次看到的 host key 会被固定；若首次链路已被中间人控制，就会固定错误指纹。高安全环境应通过独立渠道预核对 fingerprint，并使用 CLI 的 add --host-key-sha256 或 UI 的“预期主机指纹”在首次连接前预置规范的 SHA-256 pin。

R2 · 远端上传要求 hardlink 扩展

兼容边界

为证明 no-replace，提交阶段强制要求 hardlink@openssh.com；扩展缺失或报错都失败关闭，不会退回 v3 RENAME。安全边界已闭合，但不支持该扩展的旧 SFTP 服务端无法接收上传。

R3 · 本地文件系统 syscall 不可抢占

OS 边界

open、flush、sync_all、hard_link 等进入 kernel 后不能由 Tokio timeout 取消；已经启动的 blocking work 在外层 Future 超时时也可能只能 detach。owned task 与身份 reconcile 防止假成功，但病态调用可在 grace 后才改变目录。可写目录中的同用户攻击者也能持续制造 path race；这不属于不同 OS principal 的隔离。

R4 · 强杀、崩溃与 panic cleanup

协作式

正常 timeout/cancel/关闭会等待有界清理；TerminateProcess、kill -9、断电或 runtime 崩溃不会运行 async cleanup。UI Drop/panic 与 tunnel handle Drop 只做非阻塞 cancel，不能保证等待 worker、远程 forward cancel 或 listener 回收。远端/本地 .serctl-part-* 仍应纳入运维扫描；原子写测试未实施真实断电试验。

R5 · 平台验证缺口

待 CI

当前 vault v4/recovery/UI 工作树已完成 Windows 本机源码门禁，较早基线还覆盖原生 IPC、DACL、原子写穿和 daemon/direct tunnel E2E。GitHub Actions 已配置 Windows、Linux、macOS 矩阵，但尚无与本次 clean commit 绑定的远端通过证据。Windows reparse 动态测试可能在无 symlink 权限时 skip，且未做多账户 Named Pipe/vault DACL 攻击矩阵；仍需 OpenSSH/Dropbear/其他 SSH/SFTP server 的外部兼容矩阵。

R6 · 原始远端终端输出

信任输入

程序自身错误和日志会转义控制字符，但 exec/PTY 的远端输出为实现终端交互而原样发送。恶意 ANSI/OSC 可影响终端；不可信输出应重定向、下载后检查或额外转义。

R7 · call-key 的精确威胁边界

威胁模型

CLI 每次调用的 profile 口令/call-key 证明能阻止“只窃取受保护 runtime token”的同账户进程启动命令、查询状态或停止 daemon；UI 则最多五分钟保留每个 profile 口令，超管操作最多两分钟保留超管密码。token-only server context 不允许业务根帧，但该设计不防御能读取 daemon/UI/client 内存、注入进程、记录键盘、抓取 crash dump 或拥有管理员调试权限的攻击者。

R8 · tunnel listener 不是访问控制

暴露边界

L/D 本地 listener、R 发给 SSH server 的 bind 请求，以及 L/R target 都强制为 127.0.0.1；调用者没有 bind/expose/target-host 输入。R 模式还只路由 connected_address 与 originator_address 都严格解析为 IPv4 127.0.0.1 的 forwarded channel。若远端 sshd 启用 OpenSSH GatewayPorts 并把回环请求改成 wildcard，外部连接不能建立可用的 serctl 转发，但 serctl 无法保证该远端 socket 没有处于监听状态或不能被端口扫描；若连这种网络表面也不可接受，必须在 sshd 禁用 GatewayPorts 或用远端防火墙阻断。回环也不隔离同机应用。动态 D 是 SOCKS5 NO AUTH，本机客户端可通过既有 SSH 连接访问远端 SSH 主机能够到达的任意目标；回环只阻止 listener 直接外曝，不是目的地址访问控制。

R9 · TERM/KILL 不是远端进程组保证

协议边界

channel signal、EOF/Close 和 transport invalidate 会释放本地/daemon 资源，但远端 shell 可忽略信号，或子进程已经脱离 channel。需要强任务终止时，远端命令本身应使用进程组/任务控制器和服务端 deadline。

R10 · 来源标识不是签名

供应链边界

commit + dirty 只是 build script 观察到的 Git 来源信号。仓库根不监听，新增根级 untracked 文件可能需其他输入变化才重算；ignored、外部或动态构建输入也可逸出 dirty 判定。它不是签名、制品证明或可复现构建证明；可靠回滚需 clean commit/push。

R11 · v5 不兼容 v4 与更早协议

迁移边界

v5 的 endpoint/domain/protocol 已升级且没有 dual-stack。旧 v4、v3、protocol 0/bearer、protocol 2 与未知锁都在 connect 前 fail closed，不发送认证字节、不删除锁、不回退直连。活动旧 daemon 应用匹配旧 executable 正常 down；stale 旧锁只能在离线核实 PID/进程不存在、租约未持有、owner/ACL/type 安全后人工处置。

R12 · 普通进程与调试器

未隔离

v4、2-of-2 与 zeroize 保护静态数据和可控副本，但正常 SSH/恢复仍必须在普通 serctl 进程中短暂持有输入口令、KEK、key package、SSH 密码或会话材料。管理员调试器可在清零前截获或把已授权组件当作解密/签名 oracle。真正阻止调试读取需要不可导出硬件密钥或不可调试 enclave，并把完整 SSH 认证和会话密码学移出普通进程；当前版本没有实现。

R13 · catalog 明文与完整快照回滚

元数据/回滚

profile 名、host、port、随机 profile_id、generation 与 recovery id/public key 是明文元数据；不要在名称或地址字段嵌入额外秘密。AEAD/identity/generation 能发现局部改写并拒绝陈旧内存授权，却没有可信单调计数器：拥有文件写权限的管理员可回滚一份完整、内部一致的旧 vault，当前实现无法检测。

R14 · Windows 文件介质与 Linux fail-closed

恢复边界

Windows 超管密码或 U 盘 share 单独均不能恢复；两者共同使用时，普通 serctl 进程会解密再重包旧凭据。文件型介质可复制，canonical 格式和“由 serctl 迁移”不是硬件不可复制/不可重实现边界；绝对路径、create-new 与回读也不能证明卷真是 USB、已物理分离或已弹出。Linux 目前没有 root-owned offline share store 与恢复专用 target-vault 边界，因此 recovery、rotation 和 v2 migration 即使以 root 运行也明确失败关闭；root 只可从 CLI 通过 NSS --target-user 绑定并永久降权后，执行不保留旧秘密的破坏性替换，该入口不能被当成已实现的离线恢复边界。

15. 运维手册

推荐流程

  1. Windows 首次使用必须在空 v4 vault 中设置至少 12 字节超管密码，并把 create-new 生成的 2-of-2 介质直接写到受控 U 盘；绝对路径/回读不能替代人工确认卷身份，写后应弹出并物理离线保管，再创建 profile。
  2. 为每个 profile 使用长且唯一的独立口令；不要把超管密码复用为 profile 口令。名称/host/port/profile_id/generation 是明文 catalog，不要在名称中包含敏感业务信息。
  3. 通过独立渠道核对首次 SHA-256 host-key fingerprint，再让 TOFU pin 成为可信基线。
  4. CLI 的普通 profile 操作每次进程调用都重新提供目标独立口令；list/admin status 只读 metadata。status/down 也执行 generation-scoped call-key exact-intent 授权。
  5. UI profile grant 固定五分钟、admin grant 固定两分钟，操作不续期。用完即撤销；到期会停止相应 transfer/shell/tunnel 但保留 daemon，并取消或拒绝呈现 Shell/Tunnel/Command/Directory/Transfer 的迟到结果。
  6. 随机口令在 UI 中应先复制到密码管理器、勾选已保存后再提交；取消/关闭只清零且不改 vault。CLI 使用新的绝对 --random-output 路径，只有命令成功才把 receipt 当成现行口令；若 commit 失败，保留文件中的值并未生效。应选择仅当前用户可写的受控父目录，因为同 UID 对手仍可在稳定回读后删除/换名输出或替换可写父目录。
  7. Windows 忘记 profile 口令时，优先用超管 + 匹配介质执行保留式恢复并设置新口令；没有介质时只能明确选择破坏性 reset、重新输入 SSH 凭据并接受旧 pin/package 永久丢失。Linux 没有保留式恢复；跨用户破坏性 reset 必须由 root 从 CLI 指定 NSS --target-user，不可传入任意 vault 路径。UI/CLI 都不会显示旧口令。
  8. 轮转恢复介质时保留旧介质直至新介质成功落盘且 vault 提交完成；新路径必须不存在。提交后安全销毁旧介质副本。不要把 vault、vault 备份、随机口令 receipt 与 U 盘 share 存在同一在线卷。
  9. v2 vault 必须停止全部旧 daemon/直连操作，使用阻断式向导或 recovery migrate-v2 一次性为全部 profile 设置新口令并迁移到 v4；不能惰性混用 v2/v4。未发布中间 v3 也不能由 v4 load/catalog/migration，需用匹配开发期 binary/备份离线处置。Linux 当前没有可用迁移路径，应保持 fail-closed 并在隔离环境保留旧工具/备份。
  10. 为 exec/传输设置符合任务 SLA 的 --timeout-secs，不要无条件使用 24 小时上限。
  11. tunnel 的所有 listener 与 L/R target 强制为 127.0.0.1；CLI/UI 只配置端口。按 ready 输出记录 port 0 的实际端口；动态 SOCKS5 没有应用层认证，可访问 SSH 主机可达的任意目标，回环只限制 listener 外曝且不隔离同机进程。
  12. 下载 M7 evidence 后独立计算 SHA-256/验证签名，并记录 serctl commit、remote path、时间和摘要。
  13. 升级跨 IPC 协议版本时，先用与活动旧 daemon 匹配的旧 executable 正常 down，然后整体切换 client/daemon；v5 对旧 v4/v3、protocol 0/bearer、protocol 2 与未知版本锁在连接前 fail closed，不发送认证字节、不自动删除且不静默降级。
  14. 定期扫描双方目录中的 .serctl-part-*，只在确认没有运行任务后清理。

Release 体积优化

正式 Release 采用体积优先且保持可移植性的 profile：

[profile.release]
opt-level = "s"
lto = "fat"
codegen-units = 1
panic = "unwind"
strip = "symbols"

opt-level = "s"、fat LTO、单 codegen unit 与符号剥离共同压缩交付文件。panic = "unwind" 是有意保留的安全语义：终端 raw mode 恢复、敏感缓冲清零和已创建 partial 的回滚都依赖 unwind 时执行 Drop，所以不以 panic = "abort" 换取更小体积。构建不使用 UPX，避免引入运行时解包、恶意软件误报、代码签名/扫描和故障定位方面的额外发布变量；也不使用 target-cpu=native，确保同一 Windows 架构内的 Release 不绑定构建机 CPU 指令集。

依赖侧把 Tokio 的 full feature 收窄为实际使用的 fs、io-std、io-util、macros、net、rt-multi-thread、signal、sync、time，并移除已不再需要的 async-trait 直接依赖及锁定包，避免为未使用能力保留依赖和编译输入。
