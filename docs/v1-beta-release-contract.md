# serctl v1 beta release and compatibility contract

<!-- release-tag: v1.0.0-beta.1 -->

Initial release tag: `v1.0.0-beta`; an immutable failed candidate is repaired
only as a new canonical SemVer prerelease such as `v1.0.0-beta.1`.

This contract defines what may be published under the v1 beta tag. It is a release gate, not evidence that the tag already exists or has passed acceptance. A release is supported only when the tag-triggered workflow finishes successfully and publishes the exact attested assets described below.

## 1. Protected release identity

The release identity is the tuple `(repository, annotated tag object, commit, workspace version, lockfile, toolchain, artifact digest, provenance attestation)`. The tag must be canonical SemVer, must equal `v` plus `[workspace.package].version`, and must point at the checked-out commit. An annotated tag is an identified tag object, not an inherently immovable object: repository governance must prevent its force-update or deletion.

All workspace crates and all internal path dependencies are centrally inherited from `[workspace.dependencies]` and use the exact requirement `=<release-version>`; ranged internal requirements are rejected. `Cargo.lock`, the top CHANGELOG entry, README current-version marker, user-guide applicable version and architecture release marker must agree. The tag workflow fails before compilation if any identity differs.

Every repair after publication uses a new prerelease identifier and a new tag. The workflow refuses to update an existing release, but that refusal is not a substitute for enabling GitHub immutable releases where the repository plan supports them.

Before the first release tag is pushed, repository governance must protect `v*` tags from force-update/deletion and enable immutable GitHub releases where the repository plan supports them. The publish job re-reads the remote annotated tag object and refuses publication unless it still equals the object validated at preflight; this detects a move during the workflow but does not replace repository tag protection.

Tag push builds, tests and attests a candidate, but it does not by itself authorize publication. The `publish` job uses the protected `v1-beta-external-acceptance` environment, which must require independent reviewers and prevent self-review. Its environment variables name an HTTPS, create-new external acceptance record and its uppercase SHA-256. Publication downloads that record without redirects and requires the following exact JSON schema:

## 3. Compatibility window

The rollback predecessor for the first v1 beta is `v0.3.0-beta.2`.

- Vault/record compatibility: v1 beta must read and operate on an unmodified v0.3.0-beta.2 vault v4 in an isolated upgrade test. Before any mutation, the operator must make a byte-for-byte backup with ACL/owner metadata and retain the matching offline recovery medium.
- IPC compatibility: the v1 candidate is IPC v9 only, while the v0.3 predecessor is IPC v8. CLI and daemon are a matched set; a mixed pair must fail before a business frame or remote side effect. There is no silent direct-connect or old-wire downgrade.
- Helper compatibility: the shipped `serctl-xfer` reports the release version/commit and transfer protocol v1. A mismatch fails before transfer; explicit `native` fails closed, while `auto` may use only a documented fallback authorized by the same root intent. `serctl-remote` has no v1 beta runtime compatibility promise because it is not shipped or supported.
- Agent/CLI compatibility: Agent NDJSON uses `schema_version=1`; unknown fields/operations and scope substitution fail closed. Transfer and managed-tunnel object terminals/status carry daemon-generated contexts and positive monotonic revisions; first exact status-by-id may discover context, later status must bind it, and cancel always requires it. Successful daemon status, connection-identity, exec, list-dir and create-dir terminals each carry a distinct daemon-generated context and exactly `revision=1`. Source readiness remains unaccepted until exact-tag real-host evidence passes.
- Profile mutation compatibility: a profile with authenticated audit material cannot be removed in this candidate. Destructive administrative replacement of every existing profile is fail-closed on both Windows and Linux because administrator-only authority cannot authenticate the predecessor audit history. Windows 2-of-2 recovery with the administrator password and matching offline medium remains supported and preserves credentials without disclosing the old profile passphrase.
- Storage rollback: rollback to v0.3.0-beta.2 is allowed only when acceptance proves that v1 made no incompatible persisted change, or after restoring the pre-upgrade backup. Copying older executables over a live v1 daemon is never a rollback procedure.

The KeyPackage audit upgrade is explicitly one-way for the predecessor reader: `audit_seed directionally incompatible`. Once v1 persists a nonzero `audit_seed` and the initialized marker, the strict v0.3.0-beta.2 reader rejects the unknown field before it can produce a package for writing. `unknown fields must not be dropped`; no compatibility path may deserialize loosely and write a truncated predecessor package. After this mutation, `binary-only rollback is forbidden`. Rollback requires an `exact pre-upgrade vault backup` together with its matching recovery medium and preserved ACL/owner metadata; restoring only executables, only the vault, or only recovery media is not accepted.

The deterministic harness self-test rejects missing recovery media, restored
vault byte/hash drift, and ACL/owner SDDL drift as incomplete rollback sets.
That structural proof keeps formal runtime acceptance `BLOCKED_NOT_RUN`; only
an independently executed rollback of the complete disposable pre-upgrade set
can turn the corresponding release gates into evidence-backed PASS results.

KeyPackage-only evidence is insufficient. The beta-2 administrative reset path can replace a profile without first deserializing its KeyPackage, so the compatibility boundary covers both the top-level `VaultFile` and the outer per-profile encrypted record: beta-2 writes storage v4; the candidate reads both layers at v4 through v5 and writes both at v5. Every successful candidate vault mutation advances the top-level version within the same protected atomic replacement, and audit initialization reseals the affected record as v5. The beta-2 validator must reject top-level v5 before `admin_reset_profile` or any other destructive writer callback is reachable; it must also reject an outer record v5 if an interrupted or manually copied state retains top-level v4. Candidate CLI and daemon identities must both embed the exact marker `vault-storage read=v4..=v5 write=v5`; the helper has no vault access and carries no storage marker.

The executable storage fixture is candidate evidence only when its source worktree is clean and its full `HEAD` begins with the common embedded candidate commit reported by all three components. A source test from a different or dirty checkout is not transferable to the inspected binaries. The embedded storage marker and commit must both be checked; neither source constants nor an external receipt may infer a binary's storage generation.

The candidate reader accepts both the exact beta-2 four-field package and the current `audit_seed`/`audit_initialized` package. It rejects future unknown KeyPackage fields, and it rejects an initialized marker without a nonzero audit seed, before any envelope can be written. A beta-2 `unknown field audit_seed` failure against upgraded storage is therefore the required predecessor behavior. Operators must switch CLI and daemon as one matched bundle; an old CLI cannot be used to issue a Grant against current storage, and no migration path may strip fields to make that command succeed.

The compatibility window ends only when a later release contract names a new predecessor and provides tested migration and rollback evidence.

## 4. Audit evidence boundary

The candidate local audit ledger covers OperationGrant roots only. Every record has both a public hash-chain link and a keyed record MAC; the checkpoint is separately authenticated. An independent `AuditSeed`, not the IPC `AuthSeed`, derives the audit key. Rotation creates a fresh DEK and `AuthSeed` while preserving `AuditSeed` so the predecessor and successor generations can be authenticated. This prevents an old `AuthSeed` from authorizing successor IPC, but compromise of an old complete KeyPackage can still affect later-generation audit keys.

A v0.3 beta-2 package with no audit seed is upgraded only while its authenticated initialization marker is false: a versioned HMAC keyed by the DEK and bound to profile id/generation deterministically derives the crash-retryable seed, which is then persisted. There is no fallback to `AuthSeed`. Missing initialized material, a missing seed, an invalid per-record MAC, checkpoint corruption or an unmatched intent fails closed.

An exported anchor is a bounded, no-follow, regular create-new checkpoint written and verified through the same handle. Windows deliberately inherits the parent ACL so FAT/exFAT offline media remain usable, and directory flush is best-effort where Windows does not expose a portable directory-fsync guarantee. The anchor contains no secret, but custody, ACL and power-loss durability remain operator responsibilities.

The chain/checkpoint may detect unkeyed content modification, truncation, reordering and unmatched intents retained across restart. It does not provide a separate monotonic trust domain. A local administrator able to synchronously restore the vault, every generation's log/checkpoint and the manually retained anchor can roll them back to an internally consistent older state.

The v1 beta release must describe and explicitly accept this limitation; it may not claim a tamper-proof audit closure or cross-snapshot rollback detection. An independent external anchor or remote transparency log remains a stable-1.0 blocker. Implementing that stable boundary is not silently waived by publishing a beta.

## 5. Grant authority and transfer limits

The protected Grant file contains the holder private key. Its serialized profile, scope, budget and expiry metadata provide Agent-side advisory fail-fast checks and prevent unauthorized requests from reaching local file access or daemon startup; they are not the authoritative authorization state. The current daemon instance's in-memory registry revalidates the signed root intent, holder proof-of-possession, profile identity, exact scope, remaining budget and monotonic expiry. Editing a Grant file cannot expand daemon authority, and a daemon restart invalidates the registration.

SFTP fallback uses a 2 KiB chunk with one WRITE/STATUS confirmation at a time. Native uses an effective 32 KiB chunk and remains one chunk per helper ACK; reported `window_bytes` therefore equals 32 KiB, not the helper's separately negotiated maximum durability/receiver capacity. Native real-host size/hash/failure testing and the same-host `scp` comparison remain open, so this contract makes no native throughput claim.

The transfer registry allows at most 8 active transfers per profile and 48 globally. Terminal snapshots live for at most 15 minutes and are additionally capped to the newest 16 per profile and 256 globally. Identity isolation uses the random profile id, not the reusable display name.

## 6. Whole-set upgrade

1. Finish or cancel shell, tunnel, transfer, Agent and remote-command activity. Treat timeout or disconnect after possible submission as `unknown`; do not retry a mutating operation blindly.
2. Use the currently installed matching CLI to stop its daemon normally. Confirm the process, descriptor and lease have retired; do not delete runtime state to force progress.
3. Record current CLI/daemon/helper versions and hashes. Back up the vault and paired recovery material without printing their contents.
4. Verify the new release attestation and `SHA256SUMS`. Stage the entire Windows runtime bundle in a new protected directory.
5. Atomically switch the installation directory or its versioned parent reference. Never overwrite only the CLI or only the daemon.
6. Run `--version` on both binaries, confirm the same version and clean commit, then perform metadata-only status followed by an isolated profile smoke test.
7. Keep the predecessor bundle and pre-upgrade backup until the acceptance window closes.

Grant files are bound to one daemon instance. Upgrade invalidates their in-memory registration; reissue least-privilege Grants after the new daemon is verified.

## 7. Rollback

Rollback uses the same whole-set procedure in reverse. Stop the current daemon with its matching CLI, switch to the retained predecessor directory, and restore the pre-upgrade vault only when the compatibility test requires it. Validate version identity before any remote operation.

If daemon shutdown, filesystem replacement or persisted schema state is uncertain, stop and preserve evidence. Do not mix binaries, delete the runtime descriptor, truncate journals, or claim rollback success until the exact active process and persisted state are known.

## 8. Release evidence and verification

The tag workflow publishes:

- Windows runtime and separate PDB archives;
- one Linux x86_64 `serctl-xfer` runtime archive and a separate debug-symbol archive; neither may contain `serctl-remote` or jobs executables;
- the Agent JSONL contract, release contract and acceptance matrix shipped with each runtime archive;
- six CycloneDX 1.5 SBOMs: JSON and XML for the Windows-targeted `serctl-cli` and `serctl-daemon` crates, plus JSON and XML for the Linux-targeted `serctl-xfer` crate; workspace-wide or experimental-component BOMs are not release inputs;
- per-platform and aggregate provenance JSON, each including the annotated tag-object identity;
- `SHA256SUMS` covering every release file except itself;
- GitHub OIDC build-provenance attestations covering every release file, including `SHA256SUMS`.

Before aggregate provenance is written, the manifest generator requires the exact twelve input filenames implied by this matrix (two Windows archives, two Linux xfer archives, two per-platform provenance files and six component/target-specific SBOMs), rejects missing, extra, nested, reparse-point or empty inputs, and then creates `release-provenance.json` plus `SHA256SUMS` with create-new semantics. The final release set contains exactly fourteen top-level files: those twelve inputs, aggregate provenance and `SHA256SUMS`. The workflow freezes a same-handle size/SHA-256 snapshot of that closed set, names all fourteen attestation subjects and upload inputs literally rather than re-expanding a directory glob, and rechecks the snapshot after attestation and immediately before upload. The publish job starts with an absent download directory and does not trust the artifact download as an implicit continuation of attestation: after downloading it re-enumerates the exact fourteen-file allowlist, enforces per-file and one-GiB aggregate bounds before whole-file parsing, rejects directories/reparse points/empty files, parses a strict UTF-8 canonical thirteen-line non-self-referential `SHA256SUMS` only after its 4 KiB pre-read bound, rejects path and duplicate entries, recomputes every digest, and binds aggregate plus per-platform provenance to the requested version, commit, tag, annotated tag object and repository.

The GitHub OIDC subject set is exactly those fourteen formal release files: four runtime/symbol archives, two platform provenance files, six CycloneDX SBOM files, `release-provenance.json`, and `SHA256SUMS`. Each pinned `actions/attest-build-provenance` invocation receives one literal allowlisted path; no subject glob can acquire a file inserted after the snapshot. After the independent acceptance gate, the publish step copies only snapshot-matching source handles into an absent create-new staging directory, verifies the complete downloaded-release contract again, verifies GitHub OIDC provenance separately for all fourteen protected staged files, rechecks their frozen size/SHA-256 snapshot immediately before `gh release create`, and passes `gh` paths derived from the same allowlist rather than a directory enumeration. On Linux the staged files are mode 0400 and their directory is mode 0500; any ordinary missing, replaced or extra entry fails the closed-set checks. The `gh` process necessarily reopens pathname arguments, so this mechanism does not claim protection from a process that has already compromised the same runner account and can change permissions, replace a file only while `gh` opens it, and restore the snapshot before the post-publication check; runner isolation and pinned trusted workflow code remain the boundary for that capability. “Provenance” here refers only to these GitHub-generated attestations and the three formal provenance files included in the release set.

The parser-fuzz success receipt, external acceptance record, external evidence manifest, five category receipts and their GitHub Actions artifact/container metadata are not release assets and are never copied into `release-dist` or attached to the GitHub prerelease. They are independently retained publication-gate inputs bound by exact artifact ID where applicable, artifact digest, file SHA-256, strict schema and release identity. The workflow does not generate or claim GitHub OIDC build-provenance attestations for those external records; their trust comes from the documented independent owners, protected environment and byte/identity bindings, not from the release asset attestation step.

The same independent verifier opens all four archives before publication. Windows runtime contains exactly `serctl_cli.exe`, `serctl_daemon.exe`, its platform provenance and the five governance documents; Windows symbols contains exactly the two named PDBs. Linux runtime contains exactly `serctl-xfer`, its platform provenance and those five documents; Linux symbols contains exactly `serctl-xfer.debug`. Archive members must be bounded top-level regular files and are rejected as soon as they differ from the allowlist. ZIP EOCD and central-directory offsets must terminate at physical EOF; Unix link/type bits and DOS Directory/ReparsePoint bits fail closed. Linux archives use one canonical gzip member whose raw DEFLATE endpoint is followed by exactly one CRC/ISIZE trailer at physical EOF, and canonical ustar with bounded total headers, members and expanded bytes; PAX/GNU extensions and root directory headers are not accepted. `serctl-xfer` is exactly mode 0755 while debug symbols, provenance and governance documents are exactly 0644. Path traversal, nested paths, duplicate or case-colliding names, symbolic links, hard links, extended/non-regular tar members and every source-only component fail closed. Runtime member byte lengths and SHA-256 values must equal the corresponding closed `binary_components` records, symbol member SHA-256 values must equal the closed `symbol_sha256` map, and the provenance embedded in each runtime archive must byte-match the separately released platform provenance. Synthetic ZIP/tar.gz trailing-data, second-member, mode, metadata and content mutations exercise these rejection paths but are not tagged artifact or attestation evidence.

It runs `gh attestation verify` once for every filename returned by that same fourteen-file allowlist, binding each successful result to the publishing repository, release workflow, peeled commit and exact tag ref before consulting external acceptance evidence. After that evidence passes, the final publish step repeats both the complete downloaded-set verification and all fourteen attestation checks against the protected create-new publish staging immediately before release creation. Linux platform provenance must record `runtime_abi.family=glibc`, `maximum_supported=2.35`, and a valid `maximum_required` no newer than 2.35; Windows must record `windows-msvc` and `x86_64`.

The Linux platform bundler runs `readelf --version-info --wide` against the final stripped helper, requires at least one inspectable GNU libc version need, rejects a maximum above `GLIBC_2.35`, and records both the supported ceiling and observed maximum in platform provenance. Pinning the runner alone is not accepted as ABI evidence.

The formal workflow runs only for canonical `v1.0.0-beta*` tag candidates; the verifier rejects non-SemVer suffixes and requires the tag to equal the workspace version. The initial candidate is `v1.0.0-beta`; every repair uses a new prerelease identifier and never moves an earlier tag. Ordinary `main` CI is necessary development evidence but does not create or publish formal release assets.

The tagged test matrix has four native rows: Ubuntu x86_64, Windows x86_64, macOS arm64 and macOS x86_64. It checks `runner.os`, `runner.arch` and the `rustc --version --verbose` Rust host tuple before compilation. Each native row also runs the same four standalone provenance build-script fixtures through a PowerShell driver that selects `.exe` only on Windows, resolves the isolated fuzz lock with locked Cargo metadata, and runs the portable parser-fuzz boundary plus downloaded-release-set mutation verifier; this prevents an Ubuntu-only extensionless test binary or archive parser run from hiding Windows/macOS path behavior. The all-target tests on every row execute the vault v4-to-v5 storage regressions and the CLI/daemon/helper identity-contract tests. One moving `macos-latest` row, cross-compilation, or an unavailable/cancelled architecture is not dual-architecture macOS evidence. The formal workflow separately invokes the reusable bounded Linux fuzz workflow at the exact tag, and both Windows and Linux bundle jobs depend on its success. Only after all three fuzz rows pass, a read-only evidence job creates and verifies a strict create-new success receipt bound to the tag object, commit, exact reusable-workflow ref, run id/attempt, fixed matrix/toolchain/commands, source digests and zero-failure closed counts. That receipt is retained for 90 days under a run-specific artifact name; assemble and publish independently download it by artifact ID with artifact-digest enforcement and recheck its SHA-256. The exact receipt bytes, receipt digest and artifact identity are embedded inside the already published aggregate provenance, so the final allowlist remains 14 files while `Test-DownloadedReleaseSet.ps1` independently replays the receipt's closed-schema and release-identity checks. The Windows row additionally runs `scripts/Test-WindowsMultiAccountAcl.ps1` with two temporary non-administrator accounts. The gate checks the two SIDs are distinct, neither is a direct member of the built-in Administrators SID, and neither secondary-logon token has the Administrator role. Inability to obtain elevation, create/log on either account, execute every owner/DACL/read/write denial assertion, or remove and then prove the absence of both accounts and the probe root fails the tagged job; it is not reported as a pass or skip.

The exact-tag workflow configures no `actions/cache`, restore key or save-on-failure cache, and no cache is accepted as an artifact input. Every action identity is allowlisted and pinned to a full commit, and release inputs come only from fresh dedicated target/output directories in the current workflow run. Adding a cross-run dependency/build-output cache is a release-contract change and must not silently become an artifact input.

The tag build uses a fresh GitHub runner and the dedicated Cargo target directory `target/v1-beta-release`. Local `target/release` contents are never release inputs. In particular, the known local directory containing mixed v0.2/v7-era binaries is invalid evidence; the clean predecessor staging set under `target/staging-v0.3/release` remains historical evidence only and is not copied into v1 artifacts.

Before a tag exists, `scripts/New-IsolatedCandidate.ps1 -Version 1.0.0-beta.1` may build a local matched set for controlled external acceptance preparation on Windows. It refuses a dirty checkout, a workspace-version mismatch, a noncanonical full `HEAD`, Git repository redirection, or an existing candidate identity. HEAD, clean status and the full tree object are read in a before/after bracket. The approved commit is checked out into a random detached worktree below `target/candidate-sources`; Cargo runs with the requested repository as its explicit working directory and the detached worktree `Cargo.toml` as its explicit manifest. Change monitors cover tracked files in both roots and reject a source mutation even if the original bytes are restored before Cargo exits. They watch the repository root non-recursively plus only top-level directories that contain tracked paths, so high-volume ignored `target` output cannot exhaust the watcher buffer; any monitored overflow still fails closed, and the final clean/tree rescan remains mandatory. Git, Cargo and any mode tool must resolve to absolute Application files outside the repository; wildcard and repository-shadow resolution is rejected, while path, file identity, size, SHA-256 and version are recorded and rechecked. Cargo writes only to a new private GUID directory below `target/candidate-builds`; candidate files are first copied with create-new handles into a separate private directory below `target/candidate-staging`. Version output, byte size and SHA-256 are then bound to the same pinned staging file object. The script records Windows volume/file identities and random owner tokens for private roots, holds non-delete-sharing handles on the candidate parents, rejects reparse points at every cleanup/publication boundary, and rechecks every staged object immediately before publication. The detached source and private Cargo tree must both be safely removed before the same-volume no-overwrite directory move publishes `target/candidates/v1.0.0-beta.1-<12-character-HEAD>`; after that move no fallible recursive cleanup remains. Neither `target/release` nor `target/staging-v0.3` is a source or destination.

This P1/P2 constructor intentionally fails closed on non-Windows hosts. PowerShell cannot provide a portable persistent directory identity and handle-relative no-replace move with one implementation; Linux and macOS require a separate native `openat`/`renameat`/`unlinkat` boundary before local candidate construction is enabled there. A future Unix implementation must call and then read back `GetUnixFileMode`, prove the permission bits are exactly 0755, and fail when that API is unavailable; merely running `chmod` is not acceptable evidence. This platform restriction does not change the cross-platform release build matrix.

The local candidate contains exactly the host CLI, daemon and xfer binaries plus `candidate-manifest.json`. The builder executes only each binary's bounded `--version` path and requires the complete anchored identities: one common clean commit, the CLI/daemon storage marker, daemon IPC v9 and helper transfer protocol v1. Unix host binaries are reset to mode 0755 after their create-new copy. The create-new manifest binds the full 40-character `HEAD`, candidate identity, repository/candidate absolute and repository-relative paths, every byte size, runtime mode, SHA-256 and unabridged version line. It records that Cargo output and the published set were separated. Source `HEAD` and full porcelain cleanliness are rechecked after the build and immediately before publication. The dual-PS self-test uses a temporary Git repository and executable fixture to prove success, dirty-tree rejection, duplicate identity rejection, wrong-protocol rejection, private-stage cleanup, published Unix executability, and unchanged sentinels in both forbidden historical output trees.

This local set is deliberately not a release artifact: its manifest has no annotated-tag object, GitHub runner provenance, platform archive, SBOM, attestation or external acceptance record. It may be used to obtain bounded pre-tag runtime evidence, but it cannot check any exact-tag artifact or publication box and is never copied into `release-dist`. Formal artifacts continue to come only from the fresh exact-tag workflow target described above.

Example verification, after installing GitHub CLI attestation support:

```powershell
gh attestation verify .\serctl-1.0.0-beta-windows-x86_64.zip --repo StarrySky7D4/serctl
Get-FileHash .\serctl-1.0.0-beta-windows-x86_64.zip -Algorithm SHA256
```

Compare the calculated digest to the attested `SHA256SUMS`; do not trust a checksum downloaded from a different source.
